# 챗봇 역할 분리 구현 — 2026-10-23

## 실행 흐름

`사용자 발화 → LLM 구조화 해석 → 코드 검증 → 허용 도구 실행 → LLM 설명/작성 → 코드 검사 → 화면 표시/계정별 저장`

LLM은 의미 이해·설명·질문·문장 작성을 담당한다. 코드는 사실 저장, 검색 실행, 원문/자격 상태, 접근 권한, 필수 항목, 분량, 버전과 사용자 확인을 통제한다. LLM이 SQL·저장·출시 승인·신청 자격을 직접 결정하지 않는다.

## 1. 본인 사실·검색 조건·질문 분리

구현: `app/services/conversation_intent.py`.

- `TurnRequest` 하나에 본인 사실 변경, 검색 전용 필터, 제외·복원, 지급 유형, 건수, 검색어와 실행할 도구를 담는다.
- LLM이 제안한 본인 사실은 실제 발화 인용·값의 범위·인용 안에 그 값이 있는지 검증한다. 질문/가정 인용은 본인 사실로 승격하지 않는다.
- 검증한 본인 진술만 계정에 저장한다. 검색에서 지역을 제외해도 계정의 실제 지역은 유지한다.
- AI가 없거나 잘못된 구조를 반환하면 보수적인 오프라인 해석을 사용한다. 질문을 개인정보로 자동 저장하지 않는다.
- 기존 분산 검색 해석 함수는 실제 처리 경로에서 제거했다. `information_search.py`는 호환용 진입점이다.

검증: 질문이 계정의 부산·3분위를 서울·0분위로 바꾸지 않음, 가정의 사실 승격 거부, 검색 전용 지역 필터와 실제 지역 분리, 지급 유형 부정 표현과 최신 요청 건수 반영.

## 2. 검색·상세·비교·선택 도구

구현: `information_tools.py`, `information_chat.py`, `matching.py`.

- 허용 도구는 search/detail/compare/select/answer다. 상세·비교·선택은 실제로 보여준 후보 ID만 참조할 수 있다.
- 상세 조회는 해당 공고의 실제 원문 발췌·준비 서류·지급 정보·조건을 읽는다. 같은 필터로 처음부터 검색하는 것으로 대체하지 않는다.
- 제목/기관 검색어는 실제 DB 조회에 적용하고 결과 제한 전에 필터링한다.
- 검색 결과와 개인 자격 판정을 분리한다. 조건을 제외해 찾은 공고라도 실제 개인 자격과의 불일치는 표시한다.
- 도구 실행 시 모집/검토 상태를 다시 검사하고, 작성 진입 시 개인 자격을 재검증한다.

검증: 두 번째 공고 상세, 두 공고 비교, 원문·서류의 답변 전달, 마감 공고 제외, 실제 검색어 적용.

## 3. 근거 기반 응답과 표시

구현: `information_responses.py`, `app/api/chat.py`, `ChatPage.tsx`.

- LLM에 실제 도구 결과, 적용된 조건, 원래 프로필과 후보 데이터를 전달하고 답변 전체를 생성한다.
- 개인 자격 적용 전 집계와 실제 후보를 구분한다. 실행하지 않은 검색을 완료했다고 말하지 않도록 지시한다.
- citations와 claims로 공고 ID 및 지급액·일정·서류·원문 근거 필드를 연결한다. 코드가 해당 공고의 실제 필드 값 또는 정확한 원문 인용과 대조한다.
- 응답 형식·알 수 없는 후보·URL·근거 없는 숫자 검사도 유지한다. 이 검사는 자연어 의미 전체의 정확성을 보증하지 않는다.
- UI는 백엔드 답변을 그대로 표시하고 AI 응답/실패 시 대체 안내, 검색 모드·생활비 유형·지역 조건 제외를 구분해 표시한다.

## 4. 작성 상담과 사실 수집 분리

구현: `writing_conversation.py`, `writing_workflow.py`, `WritingChatPage.tsx`.

- LLM이 발화를 사실 답변/설명 질문/사실 정정/초안 문체 수정/확인/불명확으로 구분한다.
- 질문은 대화에만 기록하며 신청서 사실과 필수 항목 완료 상태를 변경하지 않는다.
- 사실 답변·정정은 사용자 발화의 정확한 인용만 저장 후보로 사용한다. 코드는 대상 문항·수집 항목·선택지·작성 가능 상태를 검증한다.
- 명시적인 사실 정정은 기존 확인·초안·검토 상태를 무효화한다. 설명 질문은 기존 초안을 무효화하지 않는다.
- 다음 필수 항목은 코드가 결정한다. 서술형 후속 질문은 LLM이 자연스럽게 표현할 수 있으며, 구조화된 선택지·동의·수치 입력 안내는 코드의 원문 지침을 유지한다.
- 초안 생성 후에도 질문과 문체 수정을 요청할 수 있도록 입력창을 유지했다.

## 5. 실제 문장 생성·재작성

구현: `essay_generation.py`, `writing_drafts.py`, `writing_workflow.rewrite_draft`.

- 서술형 문항에서는 확인한 사실을 바탕으로 LLM이 문장을 새로 작성한다. 사실의 순서만 정하는 이전 방식은 교체했다.
- 각 문단에 사용한 사실 키와 정확한 인용을 연결한다. 코드가 알려진 사실 키, 인용 일치, 사실 누락과 새 숫자를 검사한다.
- 별도 LLM 호출로 사실 추가·의미 변경·누락을 대조한다. 같은 제공자의 모델 검사이며 독립 사람 검수를 대체하지 않는다.
- 실패하면 검증되지 않은 문장을 사용하지 않고 기존 확인 사실 조합 초안으로 대체한다. UI에 AI 문장 작성과 사실 조합을 구분한다.
- 문체 수정은 확인 사실을 유지하고 기존 검토/저장 승인을 해제한다. 구조화된 값·선택지·동의·서명은 자유 문장 생성으로 바꾸지 않는다.
- 분량과 필수 항목 검사는 코드가 계속 수행하며 저장·출력 전에 사용자 검토가 필요하다.

## 6. 계정별 대화 저장·복원

구현: `information_session.py`, `information_store.py`, `/chat/session`, 프런트 복원 API.

- 새로고침·프로세스 메모리 초기화 후 계정 대화를 복원한다. 새 대화는 검색·대화 상태를 초기화하고 계정 프로필은 유지한다.
- 기본 30일(마지막 저장 기준) 복원하며, 기간이 지난 기록은 해당 사용자의 이후 저장 시 정리한다. 설정과 개인정보 안내를 갱신했다.
- 소유권과 낙관적 버전 검사를 적용하고 계정 탈퇴 시 DB 기록과 메모리 기록을 제거한다.

## 최종 검증

- 전체 Python 회귀: **2,076개 통과**.
- Edge 브라우저 통합: **4개 통과**. 실제 HTTP API와 임시 DB에서 정보 대화 표시/실패 안내, XLS/XLSX/HWP 부분 범위 작성·저장·출력을 확인했다. 전체 양식의 정확도 승인으로 해석하지 않는다.
- 추가 브라우저 검사에서 새로고침 후 정보 대화 복원과 새 대화 시작 확인.
- TypeScript 타입 검사 및 Vite 프로덕션 빌드 통과.
- 실제 DeepSeek + 실행 중 로컬 API: `3분위·3.8·서울` → `서울만 제외·다른 조건 유지·생활비 10개`를 실행. 본인 정보는 유지하고 실제 검색에서 지역만 제외했으며 후보 2건과 제목을 반환했다. 두 답변 모두 `answer_source=llm`.
- 실제 DeepSeek 문장 생성 및 별도 근거 대조: 교재비 필요·전공 수업 집중이라는 개인정보 없는 사실 2개로 새 문장을 생성해 `llm_grounded_prose` 확인. 샌드박스 내부 CLI의 네트워크 오류는 제한 밖 실행으로 재검증했다.

## 실행·제한

- 로컬 개발 서버: `http://127.0.0.1:5173/`. 최신 코드/빌드는 로컬에 반영했으며 운영 서버 배포는 수행하지 않았다.
- 개발 DB는 개발 모드의 테이블 자동 생성으로 새 테이블이 생성됐다. 운영은 기존 운영 절차대로 마이그레이션 적용이 필요하다. 기존 로컬 Alembic 이력 전체를 임의로 변경하지 않았다.
- 공고 수집 범위는 그대로다. 전국 실시간 검색이나 미검수 양식의 작성 승인을 추가하지 않았다.
- 과거 대화에서 잘못 저장된 본인 정보는 추측해 고치지 않는다. 사용자가 명시적으로 정정하면 새 해석 경로로 반영한다.
- 모델 검사·단위 테스트는 사실 진위와 전체 실제 양식 품질을 보증하지 않는다. 원문 검토와 최종 사용자 확인은 유지한다.
