## 0. 전체 그림

```
[사용자 보유 정보]          [혜택 원본]                    [규칙·검증]              [계산]           [화면]
카드 card_ids        ─┐   CardBenefit (카드·브랜드)   ─┐
간편결제·페이스페이   ─┼─▶ PayBenefit 🔵 (간편결제·굿딜 ─┼─▶ MapEvidence.rules  ─▶ estimate() ─▶ 추천 선택 🔵 ─▶ 마커·가게 상세
지역화폐·학교 제휴   ─┤        ·페이스페이, 브랜드)    │   (BenefitRules)          (기존)           (12-5 규칙)
학생증               ─┘   LocalBenefitMerchant (가게) ─┘   승인·재확인 (기존)

[매장]  상가정보 매장 🔵 ──(상가업소번호)──▶ Store + 매장 번호 🔵 ──▶ 검색 · 즐겨찾기 · 착한가격업소 통합 마커
```

## 1. 기능별 개발 방향

## 2. 데이터 구조 설계

### 2-1. 4개 층으로 나눈다

| 층 | 무엇 | 저장 위치 | 구분 |
|---|---|---|---|
| ① 사용자 보유 | 사용자가 가진 결제수단 | `users.card_ids`, `preferred_pay_methods`, `benefit_programs`, `student_credentials` | 🟢 + 값 추가 |
| ② 혜택 원본 | 화면에 보여줄 혜택 문구와 대상 | `CardBenefit` / `LocalBenefitMerchant` / **`PayBenefit` 🔵** | 🟢 + 🔵 |
| ③ 규칙·검증 | 계산에 쓰는 숫자 조건, 출처, 승인 상태 | `MapEvidence` (`rules` = `BenefitRules`) | 🟢 + JSON 확장 |
| ④ 매장 | 지도에 찍히는 가게 | `Store` + **매장 번호 🔵**, `MapLocation` | 🟠 |

**원칙:** 계산은 **승인된 `MapEvidence.rules`만** 쓴다. ②의 칸(`cap_text`, `conditions` 등)은 화면 표시용으로만 쓴다. 승인 전 혜택은 숫자 없이 `혜택`으로 보여준다.

### 2-2. 결제수단과 결제 방법

| 사용자가 고르는 결제수단 (①) | 계산에 쓰는 결제 방법 (`payment_paths`) | 비고 |
|---|---|---|
| 카드 (`card_ids`) | `card` | 🟢 |
| 카카오페이 (`kakao`) | `kakao` + **`kakao_gooddeal` 🔵** | 굿딜은 카카오페이 보유자에게 **자동 포함** |
| 토스페이 (`toss`) | `toss` | 🟢 |
| 토스 페이스페이 (**`toss_facepay` 🔵**) | **`toss_facepay` 🔵** | 따로 고른다 (얼굴 등록 필요) |
| 네이버페이 (`naver`) | `naver` | 🟢 |
| 서울Pay+·제로페이·온누리 (`benefit_programs`) | `currency` | 🟢 |
| 학생증·톡학생증 (`student_credentials`) | 결제 방법이 아니라 **자격 조건** (`rules.credentials`) | 🟢 카드·현금 등 어떤 결제와도 함께 쓰일 수 있다 |

- `preferred_pay_methods`는 글자 목록이라 `toss_facepay` 추가에 **DB 변경이 필요 없다**
- `payment_paths`는 JSON이라 **DB 변경이 필요 없다**. 검증 목록(`invalid_payment_path`)만 넓힌다
- 기존 간편결제 enum(`PayMethod`)은 매장 단위 샘플(`StoreOffer`)에 묶여 있어 **넓히지 않는다**

### 2-3. 혜택 종류별 저장 위치

| 혜택 | 원본 테이블 | 적용 단위 | `MapEvidence.kind` |
|---|---|---|---|
| 카드 할인 | `CardBenefit` 🟢 | 브랜드 (`brand_key`) | `card` 🟢 |
| 복잡한 카드 캐시백 | `card_benefit_versions` 🟢 | 브랜드 | (자체 승인 흐름) 🟢 |
| 간편결제·굿딜·페이스페이 | **`PayBenefit` 🔵** | 브랜드 (`brand_key`) 또는 업종 | **`pay` 🔵** (`MODELS`에 등록) |
| 학생증 제휴·지역화폐 | `LocalBenefitMerchant` 🟢 | 특정 가게 | `local` 🟢 |
| 착한가격업소 | `LocalBenefitMerchant` 🟢 (`goodprice`) | 특정 가게 | 할인이 아니라 가격 정보 (계산 제외) |
| 매장 단위 간편결제 샘플 | `StoreOffer` | 매장 | 105건 전부 샘플 → **새 데이터를 넣지 않는다** |

### 2-4. 신규 테이블 설계

**`PayBenefit` (브랜드 단위 결제 혜택)**

| 칸 | 예 | 설명 |
|---|---|---|
| `id` | | |
| `provider` | `kakao` / `toss` / `naver` | 결제수단 |
| `payment_path` | `kakao_gooddeal` / `toss_facepay` / `kakao` | 결제 방법 |
| `brand_key` | `GS25` | `store_brand_key()`로 정규화. 업종 전체면 비움 |
| `category` | `convenience` | 업종 단위 혜택일 때 |
| `benefit_text` | "굿딜 바코드 결제 3% 할인" | 화면 표시용 |
| `guide_text` | "카카오페이 앱 → 굿딜 → GS25 바코드 제시" | 결제 방법 안내 |
| `source_url`, `source_as_of` | | 출처 |
| `is_active` | | |

- 숫자 조건(할인율·한도·기간)은 이 테이블이 아니라 **`MapEvidence.rules`에** 둔다 (카드 혜택과 같은 방식)

**`FavoritePlace` (자주 가는 곳)**

| 칸 | 예 | 설명 |
|---|---|---|
| `user_id` | | |
| `place_key` | `sbiz:MA0101…` / `local:goodprice:…` | 바뀌지 않는 매장 번호 (2-5) |
| `label`, `address` | "스타벅스 경희대점" | 저장 당시 이름 (매장이 사라져도 목록에 남기기 위해) |
| `created_at` | | |

- (`user_id`, `place_key`) 중복 금지
- 혜택은 저장하지 않는다. 목록을 열 때마다 **현재 보유 카드 기준으로 다시 계산**한다

### 2-5. 매장 식별 구조

| 대상 | 바뀌지 않는 번호 | 구분 |
|---|---|---|
| 상가정보 매장 | `sbiz:` + 상가업소번호 | 🔵 `Store`에 `external_source`, `external_id` 칸 추가 |
| 기존 시드 매장 47곳 | 상가정보와 매칭되면 그 번호, 아니면 `seed:` + 기존 id | 🔵 |
| 지역 가맹점·착한가격업소 | `local:` + 기존 `source_key` | 🟢 이미 있음 |

- **같은 가게 합치기:** 착한가격업소·지역 가맹점을 주소 + 상호로 상가정보 매장과 연결하면 같은 번호를 갖게 되고, 기존 `place_id` 합치기 코드로 하나의 마커가 된다
- **좌표:** 상가정보 좌표를 검증 위치로 인정한다 (기존 `_public_location()`을 확장). 카카오 검색 좌표는 저장하지 않는다 (기존 결정)
- **지점 조건:** `rules.branches`, `excluded_branches`는 지점 이름 대신 매장 번호로 비교한다

### 2-6. 브랜드 혜택과 특정 지점 연결

```
매장 (스타벅스 경희대점, brand_key=스타벅스, sbiz:…)
  ├─ CardBenefit (brand_key=스타벅스)  ──┐
  ├─ PayBenefit  (brand_key=스타벅스)  ──┼─ rules.branches / excluded_branches로 지점 거르기
  └─ LocalBenefitMerchant (같은 매장 번호) ┘   (특정 가게 혜택은 번호로 직접 연결)
```

### 2-7. 학교와 학생증 제휴

| 단계 | 방식 | DB 변경 |

### 2-8. `BenefitRules` 확장 (JSON, DB 변경 없음)

| 추가 항목 | 값 | 용도 |
|---|---|---|
| `payment_paths` 값 추가 | `kakao_gooddeal`, `toss_facepay` | 결제 방법 구분 |
| `reward_timing` | `instant` / `billing` / `cashback` / `point` | 즉시·청구·캐시백·적립 구분 (동점 처리, "나중에 돌려받아요" 표시) |
| `guide_text` | 문구 | 결제 방법 안내 (원본 테이블에 없을 때) |
| `stackable_with` | 결제 방법 목록 / 비움 / `unknown` | 중복 가능 여부. **초기 계산에는 쓰지 않고 기록만** |

- 상시·이벤트 구분은 기존 `indefinite`(무기한)로 대체한다. 새 칸 불필요

## 3. 추천 알고리즘 설계 (기준만, 구현 안 함)

### 3-1. 전체 흐름

```
① 후보 모으기   내 결제수단 × 이 가게에 해당하는 혜택 (승인된 것만 숫자 계산)
② 후보별 판정   기존 estimate() → 상태(확정/조건부/해당 없음) + 예상 절약액 + 이유
③ 결제 방법당 1개   같은 결제 방법 안에서 절약액이 가장 큰 것만
④ 1위 판단     금액에 따라 1위가 바뀌는지 확인 → 추천 / 조건부 추천 / "결제금액에 따라 달라요"
```

### 3-2. 기준

| 항목 | 기준 |
|---|---|
| **추천 기준** | **예상 절약액(원)**. 할인율이 아니다 |
| **정률·정액 비교** | 같은 금액에서의 절약액으로 비교한다. 정률 = 금액 × 할인율(원 단위 내림), 정액 = 할인액(결제 금액 이하). 건당·월 한도까지만 |
| **전월 실적** | 사용자에게 묻지 않는다. 실적 조건이 있으면 **조건을 채웠다고 가정**해 절약액을 계산하고 상태는 `conditional`. 사용자가 계산기에서 실적을 입력하면 기존 엔진이 확정·해당 없음으로 바꾼다 |
| **월 한도** | 다 남아 있다고 보고 계산하고 `conditional` (기존 엔진 동작 그대로) |
| **즉시·청구·캐시백·적립** | 금액 가치는 같게 본다 (포인트 1점 = 1원). 절약액이 같으면 즉시 → 청구 → 캐시백 → 적립 순 |
| **중복 적용** | **초기에는 계산하지 않는다.** 결제 방법별로 따로 비교한다. 중복 정보는 기록만 하고, 나중에 양쪽 모두 "가능"으로 승인된 조합만 합산한다 |
| **승인 안 된 혜택** | 절약액을 계산하지 않는다. `혜택`으로 표시하고 순위에서 뺀다 |

### 3-3. 결제 금액을 입력하지 않았을 때

1위가 **금액과 상관없이 같은지** 먼저 확인한다.

| 경우 | 금액에 따라 바뀌나 | 화면 |
|---|---|---|
| 정률 할인끼리, 한도·최소 금액 없음 | 안 바뀜 (할인율 순서 = 절약액 순서) | **추천** |
| 정액 할인끼리, 최소 금액 없음 | 안 바뀜 | **추천** |
| 정률과 정액이 섞임 (10% vs 1,000원) | **바뀜** (1만원에서 같고, 그 이상이면 10%가 이김) | **"결제금액에 따라 달라요"** + [예상 절약액 계산하기] |
| 한도·최소 결제 금액 때문에 순서가 바뀌는 구간이 있음 | **바뀜** | **"결제금액에 따라 달라요"** |
| 후보가 하나 | 안 바뀜 | **추천** |

"결제금액에 따라 달라요"일 때는 후보를 간단히 보여준다.

```
결제금액에 따라 달라요
  A 카드   10%*  (많이 결제할수록 유리)
  학생증    1,000원 할인  (1만원 미만 결제 시 유리)
[예상 절약액 계산하기]
```

**바뀌는지 판단하는 범위:** 업종별 일반적인 결제 금액 구간 안에서 순위가 바뀌는 지점이 있는지 본다. 구간 값은 **추가 결정 필요** (5번).

### 3-4. 기준 금액 10,000원의 쓰임

| 쓰는 곳 | 쓰지 않는 곳 |
|---|---|
| 지도 마커에 띄울 혜택 하나 고르기 (**참고용**) | 가게 상세의 "추천" 확정 |
| 목록의 "할인 높은순" 정렬 | 절약 금액 표시 (화면에 10,000원 기준 금액을 보여주지 않는다) |
| | 절약 기록 |

- 착한가격업소는 10,000원 대신 대표 메뉴 가격을 쓴다

### 3-5. 확정 추천을 하지 않는 기준

| 상황 | 화면 |
|---|---|
| 1위가 확정 (`eligible`) | **추천** |
| 1위는 조건부, 확정 후보도 있음 | **조건 충족 시 추천** (조건부 1위) + **조건 없이 확실한 방법** (확정 1위) |
| 전부 조건부 | 1순위 없이 **확인이 필요한 혜택**으로 절약액 순 나열 |
| 금액에 따라 1위가 바뀜 | **결제금액에 따라 달라요** |
| 승인된 혜택이 없음 (`혜택`만) | 숫자 없이 혜택 목록 |
| 해당 혜택 없음 | "내 결제수단으로 확인된 혜택 정보가 없어요" |

### 3-6. 검증 방법

- 기존 기준 사례 파일(`data/map_reference_cases.json`)에 추천 선택 사례를 더해 `evaluate_map.py`로 검사한다
- 꼭 넣을 사례: 정률 vs 정액 교차, 최소 결제 금액 경계, 월 한도 도달, 조건부 vs 확정, 굿딜 vs 카드, 승인 만료

## 6. 개발 순서

### 6-1. 왜 이 순서인가

1. **형식부터.** 혜택 규칙 형식(`BenefitRules` 확장)과 저장 위치(`PayBenefit`)가 정해지지 않으면 팀원이 수집한 데이터를 나중에 다시 옮겨야 한다
2. **계산부터, 화면은 나중.** 마커와 상세는 추천 선택 결과를 보여주는 것뿐이다. 추천 선택을 먼저 만들고 가짜 데이터로 검증하면, 화면은 결과만 그리면 된다
3. **매장 번호는 일찍.** 검색·즐겨찾기·통합 마커가 모두 매장 번호에 달려 있다. 즐겨찾기를 먼저 만들고 번호를 나중에 바꾸면 저장한 데이터가 깨진다
4. **틀린 정보부터 막기.** 지금 마커는 조건과 상관없는 최대 할인율을 보여준다. 기능 추가보다 이걸 먼저 고친다
5. **선택 기능은 마지막.** 즐겨찾기·절약 기록은 기본 흐름이 동작한 뒤에 붙여도 사용자 경험이 깨지지 않는다
