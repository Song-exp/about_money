| 절약 기록 저장 | [이 혜택으로 결제했어요] → 확인 후 저장 | **수정.** API(`POST /savings/spend`)와 호출 함수(`recordSpend`)는 있다. 원래 금액·실제 금액을 받아서 저장하고, 실제 금액이 더 크면 거절한다. **하지만 이 함수를 부르는 화면이 없다** | 가게 상세에 버튼 + 금액 확인 창 연결 | P2 |
| 마이페이지 표시 | 이번 달·누적·분야·혜택 | **유지.** 마이페이지 "세이빙" 탭이 요약 API(`/savings/summary`)를 쓴다 | 항목 비교 후 부족한 것만 보완 (**확인 필요:** 가장 많이 쓴 혜택 표시 여부) | P2 |
| 예상 vs 실제 구분 | 맵은 예상, 마이는 실제 | **유지.** 기록에는 사용자가 확인한 실제 금액만 들어간다. 예상액은 저장하지 않는다 | 필요하면 예상액 칸 추가 (선택) | P2 |

관련 파일: `app/api/savings.py`, `app/models/saving.py`, `frontend/src/api.ts`, `frontend/src/pages/MyPage.tsx`

## 5. 개발 우선순위 (의존성 기준)

### 의존 관계

```
[A] BenefitRules 확장 (결제 방법·지급 방식·안내 문구)
      ↓
[B] 추천 고르기 함수 (estimate() 재사용 + 12-5 규칙)  ←  [C] 브랜드 결제 혜택 테이블 + 굿딜 재확인·적재
      ↓
[D] 마커·가게 상세 개편 (추천 1순위, 결제 방법 안내, 계산기 단순화)

[E] 상가정보 매장 + 매장 번호 + 공공 좌표 인정
      ↓
[F] 검색 · [G] 착한가격업소 토글·통합 마커 · [H] 즐겨찾기

[I] 온보딩 정리 (성별·통신사, 페이스페이)   [J] 절약 기록 버튼
```

### 순서

| 순위 | 작업 | 왜 먼저인가 | 의존 |
|---|---|---|---|
| **P0-1** | [A] `BenefitRules` 확장 | 모든 혜택 입력의 형식이다. 데이터를 넣기 전에 정해야 다시 넣지 않는다 | - |
| **P0-2** | [B] 추천 고르기 함수 + best 규칙 변경 | **지금 추천이 꺼져 있어서** 서비스의 핵심 기능이 동작하지 않는다 | A |
| **P0-3** | [E] 공공 좌표 인정 + 상가정보 매장 | **지금 지도가 0곳**이다. 검색·즐겨찾기·통합 마커가 모두 여기에 달려 있다 | - |
| **P0-4** | [D] 마커를 추천 결과로 | 지금 마커는 조건과 상관없이 최대 할인율을 보여줘서 **틀린 정보**가 된다 | B |
| P1-1 | [C] 브랜드 결제 혜택 테이블 + 굿딜 재확인·적재 | 카드 데이터가 적어도 마커를 만들 수 있다 (빈 지도 대응) | A |
| P1-2 | [D] 가게 상세 개편 | 추천 1순위, 결제 방법 안내, 계산기 단순화 | B, C |
| P1-3 | [F] 검색 · [G] 착한가격업소 토글 | 기본 이용 과정의 "가게 찾기" | E |
| P1-4 | [I] 온보딩 정리 | 성별 필수가 "최소 입력"과 맞지 않는다 | - |
| P1-5 | 카드 프로그램 재확인 기간 정책 맞추기 | 24시간마다 승인이 풀린다 | - |
| P2 | [H] 즐겨찾기 · [J] 절약 기록 버튼 · 문구 정리 · 학교 표시 | 선택 기능 | E (즐겨찾기) |

## 6. 데이터 수집 전에 반드시 해결해야 할 문제

1. **계산에 쓰는 데이터를 한 곳으로.** 지금 혜택 정보가 `card_benefits`, `local_benefit_merchants`, `store_offers`의 칸과 `MapEvidence.rules`(JSON)에 나뉘어 있다. **계산은 승인된 `MapEvidence.rules`만 쓴다**고 정해야, 수집할 때 어디에 넣을지가 명확해진다
2. **`BenefitRules` 확장 확정.** 결제 방법 이름(`toss_facepay`, `kakao_gooddeal`), 지급 방식, 안내 문구를 먼저 정해야 굿딜·페이스페이 데이터를 한 번에 넣을 수 있다
3. **기준 금액의 역할.** 정률 할인끼리, 정액 할인끼리는 금액과 상관없이 순위가 같다. 하지만 **정률과 정액이 섞이면 금액에 따라 1위가 바뀐다** (10% vs 1,000원은 1만원에서 같고, 1만원보다 많이 쓰면 10%가 이긴다). 이 경우 기준 금액 10,000원으로 1위를 확정하지 말고 **"결제 금액에 따라 달라요"로 보여주고 계산을 권해야** 한다. 기획 12-5에 이 경우를 추가할지 정해야 한다 (기획 변경이라 반영하지 않았음)
4. **매장 번호 정하기.** 상가정보의 상가업소번호를 매장의 바뀌지 않는 번호로 쓸지 확정해야 즐겨찾기·통합 마커를 설계할 수 있다
5. **굿딜·페이스페이의 실제 조건 확인 (확인 필요).** 굿딜: 1회 구매 한도, 상품권 유효기간, 통신사 할인과의 순서(캡처 메모에 "통신사 먼저 적용 후 굿딜 결제" 있음). 페이스페이: 이용 가능한 매장 목록을 어디서 얻을지, 연결 카드 혜택 적용 여부
6. **수집 방식과 약관 (확인 필요).** 굿딜 데이터는 앱 화면 캡처다. [데이터 출처·약관 결정 사항](../DB구축/데이터_출처_약관_결정사항_20261106.md)의 원칙(공식 출처, 비교 사이트 사용 금지)에 맞는지 확인이 필요하다
7. **팀원 DB의 승인 기록 상태 (확인 필요).** 팀원 DB에는 카드 승인 4건이 있다. 이 데이터를 받으면 P0-2를 실제 데이터로 바로 검증할 수 있다
